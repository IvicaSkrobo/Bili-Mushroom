# Quick Task 260821-d5g

Two review findings agreed by both reviewers, ahead of the v0.3.40 build.

## Task 1 — single delete must not claim full success

`delete_find` collects `file_failures` from `bulk_delete_finds_blocking`, then throws them
away into `eprintln!` and returns `Ok(())`. The UI shows "moved to the Recycle Bin" even
when the photo is still on disk — exactly the dishonesty the bulk path already fixed
(`CollectionTab.handleBulkDeleteSuccess`).

- `delete_find` returns `BulkOperationResult` instead of `()`.
- `deleteFind` / `useDeleteFind` pass it through.
- `DeleteFindDialog` shows a warning toast naming the number of files left behind,
  mirroring `collection.bulkDeletePartialToast`.
- `PostImportReviewDialog` ignores the value; no change needed there.

## Task 2 — deleting an already-gone find is a success

`completed != 1` currently returns `Err("Find no longer exists")`, where the old code
treated a `DELETE` hitting zero rows as a no-op. A stale list or a double-confirm now
shows a red error for work that is already done.

- After a zero-completion result, re-check whether the row exists. Gone means the delete
  already happened: report it as completed. Still there means a real failure, which the
  caller must see.
- Deliberately **not** matching on the error string, and **not** touching the bulk
  semantics — `bulk_delete_tolerates_ids_that_are_already_gone` locks those in, and for a
  batch "one of the ten was missing" is worth reporting.

## Not doing

Finding 3 from the review (aborting the whole batch when `remove_sample_for_find` fails)
stays as it is. That function returns `Ok(())` when no sample exists, so the only path to
`Err` is a genuine SQL failure — aborting an atomic transaction is correct there, and
continuing would mask a database problem. My original "inconsistency" reading was wrong.
